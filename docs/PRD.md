# stripe-license-server 产品需求（最终版 v1.0）

日期：2026-11-19 · 作者：Link Future LLC 产品经理

## 1. 定位
一套通用的序列号激活服务，供多个 App 使用，**只支持 Stripe**，全程自动，不做手工操作。这是一个独立项目，不依赖任何特定 App。项目开源，采用 MIT 协议。

## 2. 核心规则
- **多 App**：每个 App 单独配置以下内容：
  - 标识（slug）
  - 名称
  - 序列号前缀
  - 试用天数
  - 离线宽限天数
  - 一对 Ed25519 签名密钥
- **发码**：只能由 Stripe 的 `checkout.session.completed` webhook 自动生成。
  - 发哪个 App 的码、可激活几台设备，从 Payment Link 的 metadata（`app` 和 `max_machines`）里读取。
  - 读不到这两个值就不发码，并记一条错误日志。
- **设备数**：直接记在每个序列号上（`max_machines`），不设套餐表，也不记套餐名称。
- **防重复发码**：以 `stripe_session_id` 为唯一键，同一笔订单只发一次码。
  - 用 100% 折扣码下的 0 元订单不会产生 payment intent，所以 `stripe_payment_intent` 允许为空。
- **作废**：发生退款（`charge.refunded`）或拒付（`charge.dispute.created`）时，按 payment intent 找到对应序列号，自动作废，并记录作废时间（`revoked_at`）和原因（`revoke_reason`）。
- **测试码和赠送码**：同样走 Stripe，用 100% 折扣码下单获取。

## 3. 序列号与离线验证
- **序列号**：用户拿到的是短码，格式为 `前缀-XXXXX-XXXXX-XXXXX-XXXXX`，采用 Crockford Base32 编码。
  - 数据库里只存它的 SHA-256 哈希。
- **授权凭证**：联网激活成功后，服务器签发一个 JWT。
  - 签名算法为 EdDSA（Ed25519），禁止使用 HS256。
  - JWT 里包含：签发方 `iss`、App `aud`、序列号 ID `sub`、本机哈希 `mid`、设备数 `max`、签发时间 `iat`、过期时间 `exp`。
  - 不放邮箱。
- **离线验证**：App 只内置公钥。每次启动在本地依次检查：签名、App（`aud`）、本机（`mid`）、是否过期（`exp`）。
- **续期**：App 联网时在后台续签。离线宽限期默认 30 天，每个 App 可单独设置。
  - 序列号作废后服务器不再续签，宽限期一到就锁定。

## 4. 试用（由服务端记录）
- App 首次启动时，用"App 加设备哈希"向服务器登记试用，服务器返回签名的试用凭证。
- 每台设备、每个 App 只能试用一次，卸载重装和修改系统时间都不能重置试用期。试用天数由每个 App 自己配置。
- 首次启动时如果断网：先按本地安装时间开始计算试用，联网后补登记，以服务端和本地两个开始时间里**较早的那个**为准。
- 不同 App 的试用互相独立。

## 5. 设备管理
- **激活**：设备数满了就拒绝激活；同一台设备重复激活不占用新名额。
- **解绑本机**：在 App 里操作，释放一个设备名额。
- **解绑全部设备**：用于旧电脑丢失或损坏的情况。
  - 先给购买邮箱发验证码确认，确认后清空所有激活记录，并自动激活当前这台电脑。
  - 自助解绑每 30 天最多 3 次。
- **长期不联网的设备**：90 天没联网，就不再占用设备名额。
- 换电脑的流程：先解绑旧电脑，再在新电脑上激活。设备名额还有空余时，新电脑可以直接激活。

## 6. 找回序列号
- 用户输入邮箱，系统把该邮箱名下这个 App 的所有序列号重新发到这个邮箱。
- 无论邮箱是否存在，都返回相同的提示。
- 邮件从 `info@linkfuture.net` 发出。

## 7. 管理与统计（只读，需要 admin token）
- 统计接口：
  - 有效序列号数、已激活的序列号数
  - 激活用户数（按邮箱去重）
  - 激活设备总数，以及按系统和版本的分布
  - 最近 7 天、30 天活跃的设备数
  - 正在试用和试用已到期的设备数
  - 试用转付费的数量
  - 每日趋势
- 明细接口：激活设备列表、序列号列表（显示已用几台、上限几台），可以按条件筛选、分页。
- 不传 App 参数时，按 App 分组统计。

## 8. 安全
- 签名私钥、Stripe 密钥、admin token 都只放在 Cloudflare 的 secret 里，绝不能提交到仓库。
- 必须校验 webhook 签名。
- 接口按 IP 和序列号限流，激活和找回两个接口限得更严。
- 设备 ID 按"App 加机器 ID"计算哈希，同一台电脑在不同 App 里的值不同，无法跨 App 关联用户。
- 每次发码、激活、解绑、作废、试用登记、找回，都要写入 events 审计日志。

## 9. 不在 v1 范围内
- 自助补差价升级。v1 不做；需要时由管理员通过数据库修改 `max_machines`。
- 订阅制。
- Stripe 以外的支付方式。

## 10. 验收标准
1. 在 Stripe 测试模式下付款，能自动收到序列号邮件，并且能成功激活。
2. 同一个 webhook 重复送达，只发一次码；用 100% 折扣码下的 0 元订单也能正常发码。
3. 设备数达到上限后拒绝激活；解绑一台后能重新激活；自助解绑超过次数会被拒绝。
4. 退款或拒付后，序列号被作废，App 续签失败，宽限期一到就锁定。
5. 断网时，已激活的设备可以正常启动；JWT 被篡改或拷贝到别的电脑上，都会验证失败。
6. 用 A App 的序列号去激活 B App，会被拒绝。
7. 卸载重装或修改系统时间，试用剩余天数不变；首次启动断网也能开始试用。
8. 找回序列号、邮件验证码确认后解绑全部设备，这两条流程都能跑通。
9. 统计接口返回的数字和数据库一致。
10. README 写清楚部署步骤、Stripe 配置（包括 Payment Link 的 metadata 怎么填）和建表 SQL（不需要 Electron 接入示例）。
